- 🔑 уникальный идентификатор счёта
- 👤 данные владельца
- 💰 защищённый баланс
- 📊 статус счёта: активный, замороженный, закрытый
- 🔧 абстрактные методы:
  deposit(amount)
  withdraw(amount)
  get_account_info()

Реализовать конкретный тип счёта с расширенными возможностями:
- ✅ валидация входящих данных
- 🔒 логические статусы и запрет операций при неверных статусах
- 🆔 автоматическая генерация короткого UUID при отсутствии номера счёта

Создать собственные классы ошибок:
- ❄️ AccountFrozenError
- 🚫 AccountClosedError
- ⚠️ InvalidOperationError

- ✅ корректность суммы
- 🔄 проверка статуса счета
- 🛡️ защита от отрицательных значений

#### 5. Строковое представление
Метод __str__ должен показывать:
- 🏦 тип счета
- 👤 клиента
- 🔢 последние 4 цифры номера
- 📊 статус
- 💰 баланс и валюту

#### 6. Тестирование
Создать демонстрацию:
- ➕ создание активного и замороженного счёта

## Day 3 — Система Bank

### Реализованные классы

**Client** — класс клиента банка:
- ФИО и уникальный идентификатор.
- Возраст (регистрация только с 18 лет).
- Телефон и электронная почта.
- Статус клиента (`active`, `blocked`).
- Список банковских счетов.
- Пароль и счётчик неудачных попыток входа.

**Bank** — управляющий класс банка, который хранит клиентов и счета и обеспечивает выполнение банковских операций.

### Основные методы Bank

- `add_client()` — регистрация клиента.
- `open_account()` — открытие банковского счёта.
- `close_account()` — закрытие счёта с проверкой остатка.
- `freeze_account()` — заморозка счёта.
- `unfreeze_account()` — разморозка счёта.
- `authenticate_client()` — проверка пароля клиента.
- `search_accounts()` — поиск счетов по клиенту, статусу или номеру.
- `deposit()` — пополнение счёта через банк.
- `withdraw()` — снятие денег через банк.

### Безопасность

- После трёх неправильных попыток входа клиент блокируется.
- Подозрительные действия сохраняются в `suspicious_activities`.
- Попытки входа заблокированного клиента регистрируются.
- Банковские операции с 00:00 до 05:00 запрещены.
- Попытки ночных операций регистрируются как подозрительные действия.
- Перед пополнением и снятием проверяются статус клиента и принадлежность счёта.

### Дополнительные возможности

- `get_total_balance()` — подсчёт общей суммы средств на счетах банка.
- `get_clients_ranking()` — рейтинг клиентов по сумме средств на их счетах.
- Для инвестиционных счетов учитываются свободный баланс и инвестиционный портфель.

### Тестирование

Проверены:
- Регистрация нескольких клиентов и ограничение по возрасту.
- Защита от повторной регистрации.
- Открытие, закрытие, заморозка и разморозка счетов.
- Успешная и неуспешная аутентификация.
- Блокировка после трёх ошибок.
- Регистрация подозрительных действий.
- Разрешённые и запрещённые по времени операции.
- Поиск счетов и обработка некорректных параметров.
- Подсчёт общего баланса и формирование рейтинга клиентов.

### Ограничения учебной реализации

- Пароли хранятся в открытом виде. Для реального приложения необходимо безопасное хеширование паролей.
- Прямые вызовы `account.deposit()` и `account.withdraw()` обходят проверки безопасности класса `Bank`. Клиентские операции предполагается выполнять через `Bank.deposit()` и `Bank.withdraw()`.
- Ночное ограничение применяется к пополнению и снятию через `Bank`, но пока не ко всем административным операциям.
- Финансовые расчёты используют `int` и `float`. В реальной системе предпочтительнее `Decimal`.
- Общий баланс и рейтинг приводятся к базовой валюте по фиксированным учебным курсам `CurrencyConverter`.

## Day3 — Исправления по результатам Code Review

### 1. Поддержка нескольких валют

- Метод `Bank.get_total_balance()` возвращает суммы отдельно по каждой валюте и общий итог, приведённый к базовой валюте.
- Метод `Bank.get_clients_ranking()` формирует единый рейтинг клиентов в базовой валюте.
- Балансы разных валют не суммируются без конвертации (подробнее — в разделе Day4 ниже).

### 2. Безопасность банковских операций

- Зарегистрированные счета связаны с банком через атрибут `_bank`.
- Пополнение и снятие средств с зарегистрированных счетов выполняются через методы `Bank.deposit()` и `Bank.withdraw()`.
- Инвестиционные операции выполняются через `Bank.invest()`.
- Прямые вызовы финансовых методов зарегистрированных счетов блокируются без разрешения банка.
- Банк проверяет время выполнения операций и запрещает их с 00:00 до 05:00.
- Попытки ночных операций регистрируются в журнале подозрительной активности.
- Временное разрешение на операцию сбрасывается с помощью `try...finally`.
- Один объект счёта нельзя зарегистрировать одновременно в нескольких банках.

- Запрет ночных операций.
- Успешное дневное инвестирование, снятие и пополнение.
- Регистрация подозрительной активности.

## Day4 — Исправления по результатам Code Review

### 1. Переводы на все типы счетов

- Получатель проверяется через `isinstance(account, BankAccount)`, поэтому переводы принимают `SavingsAccount`, `PremiumAccount` и `InvestmentAccount`.
- Проверки статуса (`active`) и валюты сохранены; при разных валютах сумма конвертируется в валюту получателя.
- Достаточность средств отправителя проверяется с учётом его типа до изменения балансов:
  - `PremiumAccount` — лимит снятия, овердрафт и комиссия счёта;
  - `SavingsAccount` — минимальный остаток;
  - остальные счета — свободный баланс.

### 2. Единая валюта для общего баланса и рейтинга

- Добавлен класс `CurrencyConverter` с фиксированными курсами. Им пользуются и `Bank`, и `TransactionProcessor`, поэтому курсы хранятся в одном месте.
- `Bank.get_total_balance(base_currency="USD")` возвращает словарь:
  - `by_currency` — суммы по каждой валюте без конвертации;
  - `total` — общий итог в базовой валюте;
  - `base_currency` — выбранная базовая валюта.
- `Bank.get_clients_ranking(base_currency="USD")` возвращает один общий список клиентов, отсортированный по сумме всех их счетов в базовой валюте. В каждой записи также есть `balances_by_currency`.
- Пример из ревью: клиент с `2 USD` теперь стоит выше клиента со `100 RUB` (≈ 1.11 USD).

### 3. Обработка транзакций deposit и withdraw

- `process_transaction()` выбирает обработчик по типу транзакции: `_process_transfer()`, `_process_deposit()`, `_process_withdraw()`. Новый тип операции добавляется отдельным методом без изменения существующих.
- Участники операции проверяются при создании `Transaction`:
  - `transfer` — нужны `sender` и `receiver`;
  - `deposit` — только `receiver`, `sender=None`;
  - `withdraw` — только `sender`, `receiver=None`.
- `deposit` зачисляет деньги через `Bank.deposit()` с конвертацией в валюту счёта; комиссия для пополнения не предусмотрена.
- `withdraw` списывает деньги через `Bank.withdraw()`; для внешнего снятия (`is_external=True`) начисляется комиссия 2%.
- Для обоих типов действуют проверки статуса счёта, принадлежности клиенту и ночного ограничения.

### 4. Проверка работоспособности

В конец `main.py` добавлен блок «DAY4: ИСПРАВЛЕНИЯ ПО РЕЗУЛЬТАТАМ CODE REVIEW»:

- переводы на `SavingsAccount`, `PremiumAccount` и `InvestmentAccount` (в том числе с конвертацией USD → EUR);
- отказ при замороженном получателе, нарушении минимального остатка и несовпадении валюты;
- общий баланс и рейтинг в USD и RUB, ошибка при недопустимой базовой валюте;
- успешные `deposit` и `withdraw`, снятие с внешней комиссией, отказ при нехватке средств, ночью и для замороженного счёта;
- ошибки при неверных участниках транзакции;
- очередь, в которой смешаны все три типа операций с приоритетами.

Существующие сценарии Day1–Day4 дают прежние результаты, включая очередь из 10 транзакций (5 успешных и 5 отклонённых).


## Day5 — Аудит и риск-анализ

### Реализованные классы

**AuditLog** — журнал аудита:
- Уровни важности: `INFO`, `WARNING`, `ERROR`, `CRITICAL`.
- Структурные записи: время, уровень, тип события, сообщение, клиент, транзакция, подробности.
- Хранение в памяти (`entries`) и в файле `audit_log.jsonl` (одна JSON-запись на строку, UTF-8).
- Фильтрация по точному уровню, минимальному уровню, типу события, клиенту и транзакции.
- Чтение журнала из файла через `read_from_file()`.

**RiskAnalyzer** — анализ рисков операций. Признаки и баллы:

| Признак | Баллы |
|---|---|
| Крупная сумма (порог в USD, другие валюты конвертируются) | 3 |
| Операция ночью (00:00–05:00) | 2 |
| Частые операции (больше `max_operations` за `time_window_minutes`) | 2 |
| Перевод на счёт, на который клиент ещё не переводил | 1 |

Уровни риска: `low` (0–1 балл), `medium` (2–3), `high` (4 и больше). Переводы между своими счетами не считаются переводами на новый счёт. История операций и известные получатели обновляются только после успешных операций.

**AuditReport** — отчёты аудита:
- `suspicious_operations()` — операции со средним и высоким риском, с признаками и отметкой о блокировке.
- `client_risk_profile(client_id)` — риск-профиль клиента: операции по уровням риска, заблокированные и неуспешные операции, признаки риска, сигналы в журнале банка, общий уровень риска.
- `error_statistics()` — статистика ошибок по типу исключения и по причине.

**SuspiciousOperationError** — исключение для заблокированных операций. Наследуется от `InvalidOperationError`, поэтому существующая обработка ошибок перехватывает его без изменений.

### Блокировка опасных операций

- `TransactionProcessor` принимает журнал и анализатор как необязательные параметры: `TransactionProcessor(bank, audit_log=..., risk_analyzer=...)`. Без них процессор работает как в Day4.
- Перед выполнением каждой операции оценивается риск:
  - `low` — запись `INFO`, операция выполняется;
  - `medium` — запись `WARNING`, операция выполняется с предупреждением;
  - `high` — запись `CRITICAL`, клиент отмечается в `suspicious_activities` банка, операция блокируется (`SuspiciousOperationError`), балансы не меняются.
- Успешные операции записываются как `transaction_completed`, неуспешные — как `transaction_failed` с типом ошибки.

### Тестирование

В конце `main.py` блок «DAY5: АУДИТ И РИСК-АНАЛИЗ»:

- обычные операции клиента: пополнение, переводы новому и знакомому получателю, перевод на свой счёт, частые операции со средним риском;
- подозрительные операции: крупный перевод новому получателю (заблокирован), крупные снятие и пополнение в RUB (средний риск), ночная операция, крупный перевод на фоне частых операций (заблокирован);
- проверка неизменности балансов после блокировки;
- фильтрация журнала, сохранение в файл и чтение из файла;
- три отчёта аудита;
- обработка некорректных параметров.

### Ограничения учебной реализации

- Пороги и баллы риска заданы вручную и подобраны для учебного примера.
- История операций хранится в памяти и обнуляется при перезапуске программы.
- Файл журнала `audit_log.jsonl` создаётся при запуске и исключён из Git через `.gitignore`.

## Day7 — Система отчётности и визуализации

### Запуск

python -m pip install -r requirements.txt
python demo_day7.py

Для графиков нужна библиотека `matplotlib` (указана в `requirements.txt`). Отчёты и графики сохраняются в папку `reports/`, которая создаётся автоматически и исключена из Git.

### ReportBuilder (`report_builder.py`)

Класс вынесен в отдельный модуль: зависимость от `matplotlib` нужна только для отчётности, а `main.py` и демонстрации Day1–Day6 работают без неё.

**Типы отчётов** (возвращаются как словари):
- `client_report(client_id)` — данные клиента, счета, история операций, итог в базовой валюте, риск-профиль.
- `bank_report()` — счета по типам и статусам, общий баланс, топ-3 клиентов, статистика транзакций.
- `risk_report()` — подозрительные операции, статистика ошибок, распределение клиентов по уровню риска.

**Форматы и экспорт:**
- `to_text(report)` / `export_to_text(report, filename)` — читаемый текст; списки записей выводятся таблицей.
- `export_to_json(report, filename)` — JSON с отступами, UTF-8.
- `export_to_csv(rows, filename)` — таблица из списка словарей; кодировка `utf-8-sig` для корректного открытия в Excel.

**Графики** (`matplotlib`, сохранение в PNG):
- круговые: `pie_balance_by_currency()` — средства банка по валютам, `pie_transactions_by_status()` — транзакции по статусу;
- столбчатые: `bar_clients_balance()` — средства клиентов, `bar_risk_levels()` — транзакции по уровню риска;
- линейный: `line_balance_history(account_numbers)` — движение баланса счетов;
- `save_charts(account_numbers)` — построение и сохранение всех графиков.

### Изменения в main.py

- `TransactionProcessor` хранит историю балансов счетов: начальный баланс и баланс после каждой успешной операции.
- `get_balance_history(account_number)` — история баланса счёта для графика.

### Тестирование (`demo_day7.py`)

- Подготовка данных: 4 клиента, 7 счетов, 16 транзакций (успешные, ошибочные, подозрительные).
- Генерация трёх типов отчётов и экспорт каждого в TXT, JSON и CSV.
- Построение и сохранение 5 графиков.
- Проверки: все файлы созданы и не пустые, JSON и CSV читаются обратно и совпадают с данными банка, история баланса корректна.
- Обработка некорректных данных: неизвестный клиент, пустой CSV, отчёт по рискам без журнала, график без счетов, недопустимая валюта.
